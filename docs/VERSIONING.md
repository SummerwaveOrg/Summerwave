# 版本、渠道与自更新的三个标识

> 决策备忘（2026-11-26）。0.1.0 起：**客户端版本 = 发布时刻**。
> 相关代码：`lib/versioncompare.py`、`lib/selfupdate.py`、`config/configpaths.py`、
> `net/domains.py`。

---

## 1. 三个标识，各管一件事

版本号之所以会不够用，是因为它被要求同时干三件事，而它只能干好一件：

| 它在干的事 | 真正需要的东西 | 存在哪里 |
| --- | --- | --- |
| 排序「哪个更新」 | **发布时刻** | `latest.toml` 的 `version` |
| 表达「我在跟哪条流」 | **渠道** | `latest.toml` 的 `channel` + 本机 `var/config.sh` |
| 标识「我装的是哪一份字节」 | **内容哈希** | `files.txt` / 指针里的 sha256 |

拆开之后，`version` 就再也不用为「发布节奏」背锅了。

### 客户端版本 = 发布时刻

```
2026.11.26-15:52:43
YYYY.MM.DD-HH:MM:SS
```

为什么不是递增的 `1.0.7`：

- **顺序天然正确**。不用再造「预发布排在正式版之前」那套语义；
- **不会不够用**。一天发 50 次也不会有 `1.0.7.3.2` 这种东西；
- **不用维护**。发版的人不需要决定「这是 patch 还是 minor」。

代价：连续两个发布之间至少隔 1 秒。发版慢几秒不重要。

**实现**：映射成带 **epoch 99** 的 PEP 440 版本（`99!20261126.155243`）。
epoch 让任何发布标志都大于任何老式版本号（`4.7.0` 的 epoch 是 0），于是
「从老版本升上来」天然单向；同时复用 `packaging` 的比较，不自造第二套排序。

### 软件包版本仍然是 PEP 440

`jq@1.8.2`、`4.4.0-beta1`、`1.0-procursus7` —— 规则一个字都没改。
`versioncompare` 因此有两个入口：

```python
client_key(v)   # 客户端版本：发布时刻优先，老版本号一律更旧
pkg_key(v)      # 软件包版本：PEP 440 + 社区后缀
```

**混用会得到「老客户端比新客户端新」这种结论。**

## 2. 渠道：只有两条流

| 本机渠道 | 读哪个探针 | 说明 |
| --- | --- | --- |
| `stable` | `macwavedata/latest.toml` | 绝大多数人 |
| `preview` | `prerelease/latest.toml` | 想先试新东西的人 |

- **`beta` / `rc` 不再是版本属性**。它们原本是「质量阶段」，而唯一真实的需求是
  「我跟不跟这条流」。合并成 `preview` 之后，`refuse_on_prerelease` 那段
  「beta 不许自更新」的逻辑整段消失——beta 就在 preview 流里，正常更新。
- **渠道必须记在本机**（`<base>/var/config.sh` 的 `MACWAVE_CHANNEL`）。
  旧设计是从版本号后缀（`-rc`）推出来的，时间戳版本让这个推导不可能。
  这不是退步：「我在跟哪条流」本来就是状态，不是版本号的属性。
- **跨流升级走全量**：preview → stable 时，按目标版本的清单整体替换，避免两条
  流的文件混在一棵树里。

## 3. `selfupdate = "blocked"`：预留的「这一版不能自更新」

写在**指针**里，不写在版本号里：

```toml
version = "2026.11.26-15:52:43"
channel = "stable"
selfupdate = "blocked"                       # 可选
selfupdate_reason = "layout changed; run the installer once"
```

三条规矩：

1. **缺省允许**（fail-open）。字段缺失、写错、值为空 → 一律按允许处理。
   一个笔误不该让所有客户端卡死。
2. **只限制「装进这一版」，不限制「这一版能不能跑」**。`install.sh` 直接装同一版
   完全不受影响。
3. **必须给 `selfupdate_reason`**。只说「不许」不给出路，和当年那句
   「cannot be installed with selfupdate」一样恼火。

行为：发现新版 → 目标是 blocked → **不下载任何东西** → 打印原因 + 重装命令 →
`exit 0`（这是「换一种装法」，不是失败）。`--dry-run` 也报。

两道检查：`selfupdate.py`（用户看到的那条）与 `selfupdate.sh`（真正下载的那层）。

**只给四种情形开口子**，其余一律「改代码就能自更新」：
布局变更且 prune 不敢自动删、需要新解释器/新系统、换了仓库或分支、给老版本线的
回溯修复包。

## 4. 让「跨大版本必须重装」消失的那一步：prune

`sync_tree` 只会覆盖与新增，**从不删除**。升级到文件集合变小的版本（模块改名、
拆文件、换目录）时，旧文件会留在原地——旧模块待在 `lib/` 里就是「同一份代码两个
副本」，`sys.path` 一变就跑到旧代码上。表现是「升级成功但没生效」。

所以 `sync_tree` 末尾加了 `prune_tree`（声明式收敛）：

```
清单里有的            → 必须在，哈希要对（下载阶段）
清单里没有、但在管理目录里的 → 删掉
```

**边界（宁可漏删，不可越界）**：

| 允许 | 绝不碰 |
| --- | --- |
| `cli config lib net pkg surfboard man info Keys` | `Shore/`（已装包）、`var/`（状态）、`venv/`、`python/`、`downloads/` |

管理目录是一张**写死在 `install.sh` 里**的名单，不是从清单推出来的：改名之后
旧目录已经不在新清单里，从清单推就永远推不到它——而那正是必须删掉的东西。
`scripts/structure_test.sh` 盯着这张名单与组件清单同步。

有了 prune，「跨大版本要重装」这条限制就没有存在理由了：文件集合的变化和普通
升级是同一种事情。

---

## 5. 这套设计省掉了什么

- 不需要打包 `.git`：自更新只需要「指针 + 清单 + 按哈希取的内容」。
- 不需要每次发布都涨版本号：`version` 就是时间。
- 不需要「beta / rc / dev」三套分支规则：一条 stable、一条 preview。
- 不需要「跨大版本」判定：没有大版本，只有更新的时刻。

## 6. 一句话

> **版本管顺序，渠道管拓扑，哈希管身份。**
> 三者分开之后，滚动更新既不需要 git 历史，也不需要版本号递增。
